# Scope decisions

## 2026-11-13 — Initial scaffold

- **No marketplace features or schema yet.** The request is scaffolding only. Products, search, authentication, checkout, payment, seed data, and migrations are deferred until their scope is defined.
- **Blank frontend route.** React Router and TanStack Query are wired, with Tailwind's Vite plugin. There is no sample catalog, inline product content, or speculative API call. Content and its loading/error states will arrive with the first feature.
- **Health checks only.** Liveness checks the HTTP process; readiness pings PostgreSQL with a deadline. These operational endpoints allow validation without inventing domain behavior. The API requires a reachable database on startup.
- **Simple monorepo.** npm workspaces manage /web and a separate Go module manages /api. A monorepo task framework and shared generated types are deferred until needed.
- **Local development Compose.** PostgreSQL persists in a named volume; ports bind to loopback. Web runs Vite after a build check; images must be rebuilt after source changes. Production hosting, TLS, deployment hardening, and live-reload mounts are deferred.
- **Same-origin API proxy.** Vite proxies /api to Go, avoiding a development-only CORS policy. Production routing must supply an equivalent /api proxy when deployment is scoped.
- **No placeholder tests.** There is no business logic yet. Initial validation covers compilation, type checking, static analysis, and live service checks. Business logic tests are required when features are introduced.
- **Placeholder Go module identity.** example.com/game-key-marketplace/api is used until a repository URL is chosen. Rename the module and internal imports together when that happens.

## 2026-11-13 — Marketplace schema and development seed

This supersedes the initial deferral of schema, migrations, and seed data. HTTP marketplace features and frontend content remain deferred.

- **Migrations:** numbered up/down SQL files in `api/migrations` run through golang-migrate v4 with the pgx v5 driver. The command embeds SQL, so the same migration runs locally and inside the API image. Each migration is transactional; golang-migrate tracks versions, dirty state, and locks. `down` rolls back one version and deletes its tables/data. It deliberately retains `pg_trgm`, which may have existed before the application. Run migrations explicitly rather than at every API startup.
- **Identity and relationships:** bigint identity primary keys keep joins simple. A product is a platform/region-specific catalog entry with a single genre. Platform, region, and genre are text rather than lookup tables to avoid inventing a taxonomy; normalize controlled vocabulary in future ingestion. Slugs are unique URL-safe identifiers. Release dates are nullable for unknown dates. A seller offers one listing per product and currency; seller ratings range from 0 to 5 and are stored values until reviews are scoped.
- **Money:** `numeric(12,2)` prices avoid floating-point rounding. A nullable discount must be positive and below the base price. Currency is a three-uppercase-letter code; validation against ISO currencies and support for currencies with other decimal scales are deferred. Seed prices use integer cents and EUR only. Prices are per key, and cart quantities must be positive.
- **Inventory:** `game_keys` is the source of individual inventory; `offers.stock` is a nonnegative cached count of available keys. The seed initializes them consistently. Future key ingestion and checkout must update both in one transaction while locking the offer and selected keys; no checkout or synchronization triggers are introduced here. Constraints enforce available keys have no order item and sold keys have one. A composite foreign key ensures a sold key belongs to the purchased offer. Multiple keys may fulfill an item quantity. Enforcing key count equals purchased quantity, order totals equal line totals, payment state transitions, and concurrent allocation belongs to future transactional checkout logic.
- **Purchase history:** order items snapshot product/seller names and actual unit price. A composite foreign key enforces one currency per order. Users, offers, and order references are restricted from deletion when history depends on them. Mutable carts cascade on user/cart deletion; deleting an unpurchased offer removes its cart items. Order statuses are limited to pending/paid/cancelled; refunds, taxes, fees, and payment provider records are deferred.
- **Users and carts:** email uniqueness is case-insensitive. Only password hashes have a storage column; no accounts or passwords are seeded. One cart per registered user keeps ownership explicit. Guest carts, authentication, and user anonymization are deferred.
- **Homepage content:** banners store HTTPS image URLs, safe-shaped link targets, ordering, activation, and optional scheduling. Homepage blocks are ordered product collections or banner references. JSON object `config` reserves room for collection filters; typed config validation and editorial APIs will be added with homepage features. No homepage fixtures or speculative UI copy are seeded.
- **Indexes:** `pg_trgm` plus GIN on `products.name` supports substring/fuzzy search. Separate B-tree indexes on platform, region, genre, and release date support combinable filters without guessing compound query patterns. The offer uniqueness index starts with product ID; additional seller and in-stock currency/effective-price indexes support joins and price filtering. Foreign-key lookup indexes, user order history, key availability, and active homepage ordering are covered. Revisit plans using actual queries and `EXPLAIN ANALYZE`; small seed data may correctly use sequential scans. See [PostgreSQL's pg_trgm documentation](https://www.postgresql.org/docs/17/pgtrgm.html).
- **Seed safety:** a fixed random seed generates exactly 150 fictional titles, 10 sellers, 2–8 distinct-seller offers per product, and 5–30 fake keys per offer. Every key is visibly marked `FAKE-NOT-REDEEMABLE`; HTTPS placeholder URLs avoid copyrighted image downloads. The entire insert runs in one transaction, with an advisory lock plus catalog table locks. A populated catalog is rejected, not truncated or silently overwritten; reruns therefore cannot duplicate inventory or restore sold keys. Failure rolls back all rows (identity sequences can still have gaps). Placeholder image rendering requires network access.
- **Key storage scope:** plaintext `key_value` is appropriate only for these fake development keys. Real-key encryption/key management and restricted delivery endpoints must be designed before handling actual inventory; never expose keys in catalog responses or logs.
- **Validation:** unit tests cover deterministic generation, money formatting, bounds, distinct sellers, and discounts. Opt-in integration tests require an empty database whose name ends in `_test`, exercise migration up/down/up, seed repeat refusal, forced seed-failure rollback, inventory consistency, and invalid purchase/key constraints. No application database is erased by the test suite.

## 2026-11-13 — Product listing API

- **Contract:** `GET /api/products` returns `data`, `pagination`, and `facets`. It supports single-valued platform/region/genre filters, `q`, inclusive `min_price`/`max_price`, `sort`, `page`, `page_size`, and optional `currency`. Defaults are page 1, 24 items, popularity sorting, and EUR. Limits are 100 items per page and 1,000,000 pages; offset pagination is sufficient for this assignment. Every sort ends with product ID to keep ties deterministic; concurrent catalog edits can still shift offset pages.
- **Available price:** the minimum of `coalesce(discount_price, price)` across offers with positive stock in the requested currency. Products without such offers are omitted. Price filtering happens after computing that minimum, so a more expensive offer cannot make a cheap product pass a minimum-price filter. Stock is the inventory cache established by the schema; the API does not scan key secrets or repair inventory drift.
- **Currency and precision:** comparing different currencies would be misleading, so the endpoint accepts a three-letter currency code and defaults to seed currency EUR. No currency conversion is performed. Prices are JSON decimal strings with two fractional digits, and input amounts are parsed without floating point. Unknown but correctly shaped currency codes return empty results.
- **Sorting:** `price_asc`, `price_desc`, `popularity`, `newest`, and `name`. Popularity is total quantity in paid order items across the product's offers, excluding pending/cancelled orders; it is computed from history rather than fabricated or stored separately. Newest means release date descending, with unknown dates last. Name means case-insensitive ascending using the C collation for predictable ordering. Popularity computation and offset paging may need denormalization/cursors at larger scale.
- **Search:** `q` performs case-insensitive literal substring matching on product name via `ILIKE`, compatible with the existing trigram GIN index. Percent, underscore, and backslash are escaped as literal characters; SQL values are bound parameters. Typo-tolerant similarity ranking, description search, and relevance sorting are deferred. Sort SQL comes only from an internal allowlist.
- **Facets:** platform, region, and genre arrays contain `{value, count}` for distinct products matching all active filters (including the selected facet itself, search, currency, and price), before pagination. These are conjunctive counts, not counts after removing each facet's own selection. Zero-count values are omitted; empty results use empty arrays. Numeric price ranges are handled by bounds rather than arbitrary price-bucket counts. Multi-select filters and disjunctive facets are deferred until the UI needs them.
- **Consistency:** one PostgreSQL statement computes products, total count, and facets using the same snapshot, including totals on pages beyond the last page. Counts do not multiply when a product has several offers. No new migration is required.
- **Validation and errors:** unknown/repeated/empty parameters, invalid encodings/control characters, oversized text, unsupported sorts, out-of-range pagination, invalid money, and inverted ranges return 400. Unknown well-formed facet values return zero matches instead of requiring a separate taxonomy query. Error envelopes are `{error:{code,message,field?}}` across listing failures, readiness failures, route misses, method errors, and recovered panics. Database details are logged server-side, never returned. Database work has a five-second deadline (504 on expiry); unexpected failures return 500.
- **Tests:** table-driven parser and HTTP tests cover invalid inputs and consistent errors. Disposable PostgreSQL tests cover all sort modes, paid-only popularity, discounted/out-of-stock prices, currency isolation, combined filters, literal search, pagination/empty pages, and product-level facet counts. The frontend remains unchanged.

## 2026-11-13 — Typo-tolerant search and suggestions

This supersedes the literal-only search decision above.

- **Shared matching:** listing and suggestions use the same escaped `ILIKE` substring predicate plus pg_trgm whole-name (`%`) and word (`%>`) similarity operators. Word matching catches a misspelled word inside a longer title without requiring the query to resemble the whole title. The operators and ILIKE can use the existing `products_name_trgm_idx`; a bare `similarity(...) >= threshold` filter would not provide the same index path. No migration or separate search service is needed. See [PostgreSQL pg_trgm operators and index support](https://www.postgresql.org/docs/17/pgtrgm.html).
- **Thresholds:** whole-name similarity uses **0.30**, PostgreSQL's default; word similarity uses **0.50**, lowered from its default 0.60. Measured examples: `cyberpnk` versus `Cyberpunk 2077` has whole similarity about 0.412 and word similarity about 0.667; `witcer` versus `The Witcher 3: Wild Hunt` has whole similarity about 0.208 but word similarity about 0.571. Thus 0.50 admits the requested misspelling without lowering whole-title similarity enough to broadly admit weak matches. These are initial heuristic thresholds, covered by fixtures rather than a claim of universal linguistic accuracy; tune against real query relevance data later.
- **Short inputs:** fuzzy matching starts at four Unicode characters to reduce noisy matches from very short queries. Two/three-character suggestions use literal substring/prefix matching only. One-character suggestion queries return an empty array without a database call; listing still supports literal one-character searches. Missing/blank `q` is a 400 on the suggestion endpoint; the maximum remains 200 characters.
- **Ranking:** exact case-insensitive name first, then literal prefix, then literal substring, then fuzzy-only matches. Within each tier rank by `similarity(name,q)` descending, then `word_similarity(q,name)` descending, then product ID. `fifa 2` therefore prefers a literal partial title match over a fuzzy result. Listings with `q` default to the new `relevance` sort; explicit price/popularity/newest/name sorts override relevance while retaining the same candidate set. Listings without `q` still default to popularity. Facets and price filters continue to operate on all matching products.
- **Connection safety:** thresholds are set with `SET LOCAL` inside the same transaction as each search query. They do not depend on role defaults or leak into pooled sessions. Read results still come from one statement/snapshot. Non-search listings avoid this extra transaction.
- **Suggestion contract and speed:** `GET /api/search/suggest?q=...&currency=EUR` returns `{data:[{id,name,slug,image_url}]}` with at most eight available products in relevance order. Availability/currency match the listing; results are distinct products, not duplicated offers or distinct names. The query uses an indexed name predicate, an availability EXISTS lookup, and LIMIT 8; it omits price aggregation, popularity, totals, and facets. A one-second request deadline bounds database work. No cache, frontend debounce, or arbitrary candidate truncation is added; broad short terms may still scan many rows, and production latency needs measurement on production-sized data.
- **Testing:** table-driven PostgreSQL cases cover `cyberpnk`, `fifa 2`, and `witcer`, exact/prefix/substring/fuzzy precedence, case insensitivity, no matches, literal wildcard escaping, availability, shared listing/suggestion order, explicit sort overrides, filter preservation, stable ties, and the eight-result cap. Fixtures live only in disposable test databases; the fictional development catalog is unchanged. HTTP tests cover validation, failures, and timeouts with the existing JSON error envelope.

## 2026-11-13 — Product details and seller offers

- **Endpoint:** `GET /api/products/{slug}` returns `{data:{...product fields,offers:[...]},similar_products:[...]}`. Slugs are exact, case-sensitive matches using a bound parameter. An unknown slug returns 404 with the standard `not_found` JSON error. An existing product remains accessible even without offers or available stock; empty lists are `[]`, and unknown release dates remain null.
- **All seller offers:** include every offer, including sold-out inventory and all currencies. Each contains ID, nested seller ID/name/rating, base `price`, nullable `discount_price`, `effective_price`, currency, and stock. Monetary values remain decimal strings; seller rating is a numeric value on the schema's 0–5 scale. The effective price is the discount price when present, otherwise the base price. Sort ascending by effective numeric price, then currency and offer ID for deterministic ties. Because all currencies are included, this ordering compares nominal amounts only; it is not an FX-normalized cheapest-offer claim. Consumers must display currency and must not treat a foreign-currency nominal amount as directly comparable buying power. A seller can appear more than once when offering multiple currencies, consistent with the existing uniqueness constraint.
- **Similar products:** return at most eight distinct available products with the same genre, excluding the requested product. Prefer matching platform, then matching region, then product ID. Availability means at least one positive-stock offer in any currency. Compact summaries contain ID, name, slug, image URL, platform, region, and genre; no ambiguous cross-currency summary price is supplied. This is deterministic catalog-based similarity; personalized recommendations and behavioral ranking are deferred. Return an empty array if no suitable products exist rather than unrelated fallback items.
- **Consistency and privacy:** one SQL statement retrieves details, seller offers, and similar products from one snapshot. Explicit response fields exclude game keys, user details, and internal timestamps. No schema migration is required. The existing five-second timeout and consistent JSON error envelope apply.
- **Tests:** table-driven HTTP and PostgreSQL tests cover successful details, slug forwarding, unknown/case-mismatched/injection-shaped slugs, database errors/timeouts, all sellers/currencies, discounted sorting, sold-out offers, no offers, live seller ratings/names, similar-product preference/order, exclusion of self/unavailable products, the eight-item cap, and empty arrays.

## 2026-11-13 — Cookie authentication

- **Endpoints and identity:** register accepts email/password and returns 201 with the public user; it does not automatically log in. Login returns the public user and sets the session cookie. `/api/me` returns the authenticated user. Logout is idempotent and returns 204. Email is trimmed/lowercased and protected by the existing case-insensitive database unique index; duplicate registration returns 409 (an explicit account-existence disclosure). Login uses the same generic 401 for unknown emails and wrong passwords.
- **Passwords:** bcrypt's default cost 10, unique random salts from the library, and a dummy hash comparison on unknown emails. Passwords require at least 12 Unicode characters and at most 72 UTF-8 bytes (bcrypt's limit), are not trimmed, and never appear in responses or application logs. JSON credential bodies are limited to 4 KiB, reject unknown fields/trailing JSON, and require application/json. Email verification, password reset/change, MFA, and compromised-password screening are deferred.
- **JWT and logout:** HS256 only, a required secret of at least 32 bytes, fixed issuer/audience, required expiry, issued-at validation, and positive user IDs. Sessions last 24 hours; no refresh tokens. A random 256-bit JWT ID references `auth_sessions` added by migration 000002. Authentication verifies the signature/claims and checks the live session/user in PostgreSQL. Logout deletes that session, preventing replay even if its JWT was copied; user deletion also revokes sessions by cascade. Revoking one device does not log out other devices. This adds a database lookup per authenticated request in exchange for reliable revocation. Expired sessions for a user are cleaned during login; a periodic global expiry cleanup is deferred.
- **Cookies and cross-domain deployment:** the JWT is only in the `marketplace_session` cookie, with HttpOnly, Path=/, and no Domain attribute (host-only). `COOKIE_SECURE` defaults true in Go; local Compose explicitly defaults false for HTTP development. `COOKIE_SAMESITE` accepts lax (default), strict, or none; none requires Secure. Cross-site deployment needs HTTPS, none+Secure, explicit frontend origin configuration, and browser fetch with credentials included. Cookie Domain sharing is unnecessary when the browser sends cookies to the API's own host. Browser third-party-cookie policies can still block cross-site cookies; same-site proxy hosting avoids that limitation. See [MDN cookie configuration](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
- **CSRF/CORS:** all unsafe HTTP methods require `X-CSRF-Protection: 1`. This non-simple header forces browser preflight cross-origin. Exact comma-separated `AUTH_ALLOWED_ORIGINS` controls credentialed CORS and checks any supplied Origin; wildcards, null, and unlisted origins are rejected. CLI requests may omit Origin but must supply the custom header. This protects registration/login/logout and future checkout writes even with SameSite=None. SameSite alone is insufficient for cross-site use; see [MDN CSRF guidance](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF). No CSRF token endpoint is needed with this explicit-origin/custom-header policy. Auth responses and protected routes use Cache-Control: no-store.
- **Rate limiting:** shared registration/login budget of 10 attempts per peer IP per 15-minute fixed window, including successes and invalid bodies. Return 429 with Retry-After. Mutex-protected state is bounded to 10,000 IPs and expired entries are cleaned; new IPs fail closed at capacity. This is per-process and resets on restart, sufficient for the single-instance assignment. A shared limiter and edge abuse controls are deferred. Removed unconditional RealIP trust: clients cannot evade limits with X-Forwarded-For. Behind Vite or a reverse proxy users may share a peer-IP budget; production needs a trusted proxy strategy before forwarding client IPs.
- **Authorization scope:** middleware validates identity and attaches the public user to request context; `CurrentUser` exposes it to handlers. `/api/me` and the full `/api/checkout` and `/api/orders` route trees require authentication. Purchase/order business endpoints do not exist yet: unauthenticated calls return 401 (assuming valid CSRF headers for writes), authenticated calls currently return 404. Future order handlers must still enforce owner-based access using the authenticated ID; authentication alone is not object-level authorization. Other catalog endpoints remain public.
- **Configuration:** startup fails on missing/short signing secret, invalid cookie settings, or missing/invalid allowed origins. A random secret was generated only into the ignored local `.env`; `.env.example` contains an empty placeholder. Rotate the secret to invalidate all JWTs. No migration seeds real accounts.
- **Tests:** password validation/hash checks; forged/expired/wrong-algorithm/issuer/audience JWT rejection; logout replay prevention; limiter concurrency/cap/reset; cookie/SameSite configuration; CSRF and CORS; and real PostgreSQL-backed HTTP registration, duplicate email, login, me, logout, persisted expiry, user deletion, protected routes, and rate-limit spoofing. Catalog/seed migration tests now roll back both migrations. No frontend auth UI is added.

## 2026-11-13 — Independent homepage blocks (modular monolith)

- **Module boundaries:** `internal/home/banners`, `bestsellers`, `deals`, and `newreleases` each own their repository SQL and HTTP handler. They never import or call each other. The router composes their endpoints; the shared `home/block` package contains only transport DTOs, currency validation, deadline/error handling, and JSON decoding. This is a **modular monolith**: explicit feature boundaries, one Go process/deployment, one database, and in-process infrastructure reuse, rather than independently deployed services. The shared database/read model is an intentional coupling, not a claim that these are already microservices.
- **Splitting a block into a service:** move that block's handler/repository behind a separately deployed HTTP process while keeping its JSON contract and `/api/home/...` route stable through the gateway. Initially it could use read-only access to the same tables, but that retains database coupling. A proper split gives the block its own read model/database, populated by catalog/offer/order-paid events (with outbox delivery, idempotent consumers, and backfills). Best-seller totals are a natural projection. Move its block configuration, observability, timeout/retry policy, and scaling with it; keep browser requests independent. Accept eventual consistency across blocks rather than distributed transactions for homepage reads. A service is justified only when separate ownership/scaling/deploy cadence outweighs that operational cost.
- **Content ownership:** every endpoint returns `{title,data}`. Titles and activation come from `homepage_blocks` rows keyed by `banners`, `best-sellers`, `deals`, and `new-releases`; missing/inactive configuration returns an empty title and array. React contains only layout, endpoint keys, and operational loading/error/retry copy. It renders no fallback catalog, marketing title, or banner when the API has no content. Each block has an independent TanStack Query request/cache/error state so one failure does not suppress the others. Block order is fixed in the composition for now; editorial reordering and a layout endpoint are deferred.
- **Banners:** read active rows in `banners` whose start time has arrived and whose end time has not passed, ordered by position/ID and capped at eight. The homepage block's banner reference satisfies the existing schema; the endpoint's collection is driven by the banners table. Seed links target real homepage section anchors. Images are external generated placeholders.
- **Best sellers:** aggregate `order_items.quantity` from paid orders across a product's offers, then select available products and their lowest current effective price in the requested currency. Aggregate before joining current offers so multiple sellers cannot multiply sales counts. Pending/cancelled orders do not count. Rank all-time units descending, ID ascending, limit 12. Rolling sales windows and a precomputed sales projection are deferred.
- **Deals:** one card per product with a positive-stock discounted offer in the requested currency. Display the cheapest discounted offer and its corresponding original price, ranked by percentage saved descending, effective price, then product ID; limit 12. This may differ from the listing's cheapest overall offer if another seller has a cheaper undiscounted offer. Never pair the discount with another seller's original price. The current schema has no promotion dates, so “active” means a non-null valid discount on an in-stock offer; scheduled promotions are deferred.
- **New releases:** latest known release dates no later than CURRENT_DATE, excluding future/unknown dates and unavailable products, with lowest available effective price. Rank release date descending then product ID, limit 12. “New” means latest releases, not a fixed recency window, so the fictional historical catalog remains usable.
- **Currency and errors:** optional uppercase `currency` defaults to EUR for product blocks; banners accept it but have no price filtering. No conversion or mixed-currency price comparisons. Money remains decimal strings. Queries use one statement per block and a three-second deadline; failures retain the API's JSON error envelope. No distributed cache or new indexes are added without observed query-plan needs.
- **Seed integrity:** fresh seed runs now also add three banners, four block configurations, one non-login demo sales account, and 12 paid orders representing 24 keys. Order totals/snapshots match allocated fake keys, and stock decreases in the same transaction. `seed -homepage` safely adds these to the existing fictional catalog without rebuilding it; an ownership marker makes repeats no-ops, while conflicting/partial block configuration is rejected. It requires the known 150-product demo catalog and never resets real data. Earlier “no sales/homepage seed” decisions are superseded.
- **Validation:** PostgreSQL tests cover banner schedules/activation/order, paid-only sales and duplicate-seller aggregation, discounted-offer prices, currency isolation, release-date bounds, missing/disabled blocks, and independent block behavior. Seed tests verify sales quantities, sold-key allocation, stock consistency, and idempotent additive seeding. Frontend build and browser QA verify the API-driven homepage; no cart/product-detail UI is added.

## 2026-11-13 — Purchase flow and complete frontend

These decisions supersede earlier notes deferring commerce and frontend pages.

- **Transaction and inventory:** cart mutations and checkout serialize on the user's cart row. Checkout locks offers in deterministic ID order, reads prices from PostgreSQL, locks available keys with `FOR UPDATE SKIP LOCKED`, creates order/item price snapshots, allocates keys and decrements stock in one transaction. A payment decline or insufficient keys rolls everything back. The concurrency test keeps one buyer's payment pending while a second buyer competes for the last key; exactly one succeeds. A separate test holds a key lock to exercise SKIP LOCKED explicitly.
- **Mock payment scope:** the provider is an interface with deterministic success/decline test numbers. It runs inside the database transaction solely for this mock assignment. A real provider cannot be rolled back by PostgreSQL: production needs payment authorization/capture, durable idempotency, reservation expiry and reconciliation/outbox workflows. No real card processing or card storage is implemented.
- **Idempotency:** migration 000003 adds a unique user-scoped checkout token. A repeated successful token returns its existing order before checking the now-empty cart. The browser retains the token in sessionStorage for the current cart fingerprint; declined attempts may retry. This avoids duplicate orders after a lost success response. Order access is always scoped to the authenticated user, including retries.
- **Money and limits:** integer cents in business logic and decimal strings in JSON avoid floating-point price tampering. Cart totals use unrestricted numeric aggregation to avoid display overflow; checkout rejects totals beyond the schema's range. One currency per cart, at most 50 lines and 10 units per offer bound work. Cart additions do not reserve keys. Order history uses 20-item pages; order/key reads use one SQL statement rather than per-row network queries. Bounded per-line checkout writes are required for individual allocations.
- **Frontend content and state:** API data supplies all catalog/marketing content. Interface labels, validation and operational messages are static centralized copy. URL state drives store/search filters and navigation; server fuzzy-match metadata drives the “did you mean” hint without inventing a corrected title. Similar-product summaries have no price because the endpoint intentionally omits an ambiguous cross-currency price. Home composition remains independent modules, queries and failure states.
- **Session and accessibility:** native dialog provides focus containment/Escape handling for the mobile drawer; focus indicators, explicit input labels, semantic controls, live statuses and reduced-motion support are shared. The carousel advances manually to avoid unsolicited animation. Logout removes private query data while updating the existing session observer. Clipboard errors have a visible fallback. Native HTML validation is supplemented by client checks and authoritative server validation.
- **Design reference and remaining differences:** no reference screenshots were supplied. The implemented dark purple/blue palette, yellow purchase accents, compact product grid, seller comparison and responsive header are inspired by the requested marketplace style, not a claim of pixel parity with Eneba. Original Keyspace placeholder branding, generated placeholder cover/banner imagery, system-font fallback, simplified navigation/footer and manual carousel remain deliberate differences. Localization, regional currency conversion, marketing CMS administration, wishlist, taxes/fees, real payments and full Eneba promotional surfaces are outside this assignment. No Eneba logos or assets are copied.
- **Review fixes:** strict checkout JSON rejects client price/owner fields; SQL uses bound values and allowlisted sorts; ownership is checked in order/cart queries. Corrected order-query parsing so malformed/unknown parameters cannot be silently accepted; cart numeric sums cannot overflow the display cast. Fixed stale session observers after logout, duplicate hidden filter forms, ambiguous form labels, clipboard permissions in the test context, control-border contrast, the missing accessible name on the cart cover link, and a selected filter option being removed during asynchronous facet refresh (covered by a browser regression assertion). Updated the vulnerable transitive minimatch dependency through an npm override; the audit reports zero known vulnerabilities. Session IDs, keys and payment values are not logged.
- **Validation scope:** Go race-enabled unit/integration suites cover parser tables, auth/CSRF/revocation, search misspellings, product offers, home queries/seed integrity, rollback, ownership and concurrent key allocation. ESLint, TypeScript production build, Prettier and dependency audit supplement Chromium E2E and Axe checks. Automated accessibility checks are not a substitute for exhaustive assistive-technology testing; browser coverage is currently Chromium, with other engines deferred.

- **Final verification result:** all Go packages passed `go test -race ./... -count=1` with all five PostgreSQL integration suites enabled; `go vet` passed. All four Chromium E2E scenarios passed, including Axe checks and order-owner isolation. Production build, ESLint, Prettier and npm audit passed (zero reported vulnerabilities). The additive migration was applied to the local development database and all three Compose services are healthy.
